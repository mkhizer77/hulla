# @hulla/server

The Hulla runtime modules for Nakama (ADR-0002): RPCs, hooks, the table core and the game modules, written in TypeScript and bundled into one file that Nakama's embedded JS runtime loads.

## Layout
- `src/main.ts`: `InitModule`, the one function Nakama calls at start-up; everything registers there.
- `src/rpc/`: RPC handlers. `hello` is the smoke test every environment answers; `table_create` makes a table match and registers its room code; `table_join_by_code` resolves a code to a match; `presets_get` serves the presets bundled from `content/presets`; `voice_token` signs a LiveKit room token for a presence at the table (ADR-0024).
- `src/services/`: `table_registry.ts` (room codes in the `table_codes` storage collection with region and expiry), `livekit_token.ts` (the HS256 room token; its test checks it against Node's crypto and the integration test against the compose LiveKit) and `bytes.ts` (HMAC and base64).
- `src/content/`: content files bundled at build time; `pnpm content:validate` checks them against their schemas and the engine.
- `integration/`: scripted `nakama-js` clients against a live Nakama (`pnpm --filter @hulla/server test:integration` with `HULLA_NAKAMA_HOST` set); CI runs it in the compose job.
- `src/games/thulla/`: the Thulla host (`host.ts`: moves in, events out, the legal mask per turn, the seed reveal) and `match.ts`, the named match callbacks InitModule registers.
- `src/match/registry.ts`: game id to host and match module name.
- `src/services/social.ts` and `src/rpc/social.ts`: friends on Nakama's own friend graph (requests, accept, decline and block through the client's friend API); the server adds `friend_add_by_code` (the friend-code path, 500 friends at most), `favourite_set` (ten pinned mutual friends) and `social_overview` (favourites plus the Recent Players cards). Every completed round writes the last fifty co-players per player into `recent_players`.
- `src/services/presence.ts` and `src/rpc/presence.ts`: presence (GDD 10.4). Nakama's session tracker says who is online; the match binding writes the table a player sits at into `presence` on seat join and leave; `presence_set {away}` marks the app in the background; `table_list_friends` returns every friend with a state (`lobby`, `round`, `online`, `away`, `offline` with last seen, `hidden` when the friend hides presence) and, when seated, the live table (match id, code, open seats, `joinable`), joinable lobbies first for the Home hero.
- Spectators (GDD 7.7, 9.10): friends of someone seated only, ten at most, honouring the `spectators` preset toggle; hands are never in a spectator's view. A late arrival during a round watches and takes the next free seat when the round ends; the host's `seat_spectator {userId}` seats a spectator now, or at the round end while one is in progress; `table_state.spectators` lists who is watching. The match label carries `watching` and `watchable` for the friends list.
- Text chat filters (GDD 11.1, 9.4): the before-message hook masks listed words after undoing spelling evasions (lookalike digits, separators, stretched letters) in English, Roman Urdu, Roman Hindi, Urdu script, Devanagari and Bengali; a `family` room blocks the message instead (`content.filtered`); a guest (nothing linked) at a public table may not free-text until linked (`auth.not_linked`). The lists come from `content/chat-filters/v1.json` and are replaced live through `chat_filters_set` (server key only; `chat_filters_get` shows what is in force). `mute_set` and `mutes_get` keep a player's mutes across devices; the client hides a muted player's text, quick chat and emotes.
- Block and report (GDD 10.11, 24.3): `block_set {userId, blocked}` records the block both ways (`blocks`), mutes both ways, blocks on Nakama's friend graph and refuses friend requests in either direction (`social.blocked`); the `MatchmakerAdd` before-hook stamps every ticket with its owner's id and excludes blocked players, so a blocked pair never matches. `report_create {userId, reason, tableId?, roundId?}` stores the report under the system user with the table's chat from the last seven days (the chat hook logs accepted lines per room in `chat_log`) and the target's card; three reports from distinct players within 24 hours, one per table, mute the target for 24 hours (`moderation`, `social.muted` on text). `reports_list` and `admin_chat_logs_purge` take the server key only.
- Moderation tooling (GDD 24.3, ARCHITECTURE 8.11): `admin_sanction {userId, action, reason, hours?, permanent?, device?}` applies a warning, a text mute, a voice suspension or a ban (with the account's devices when `device` is set) or `clear`, each with expiry, kept with the player's strike history in `moderation`; the match binding refuses a banned account at join (`auth.banned`), the before-authenticate hook refuses a banned device, `voice_token` refuses a suspended voice (`voice.suspended`). `admin_table_inspect {matchId}` and `admin_round_replay {tableId, roundId}` (the round rebuilt from its seed, rules and moves; the hashes must agree) and `admin_audit_list` round out the admin surface; every call writes an audit row. Admin RPCs take the server key, or a session whose user id is in `HULLA_ADMIN_USER_IDS`. `sanctions_get` shows a player their own active sanctions.
- Progression and the ledger (GDD 12.2, 12.3, 13.2, D2): at the end of a completed round the binding computes XP (finish position, thullas given, a clean round, the friend bonus) and coins (finish position, the login streak, the daily soft cap at local midnight from the client's `tzOffsetMinutes`) per seat, applies level-ups with their coin and gem grants and titles, and credits the wallet through `services/ledger.ts`: every change is a Nakama wallet update with the ledger on, keyed by a source id (`table:round:round`, `level:n`), so a retry pays nothing twice. `wallet_get` returns balances and the newest lines; `progress_get` the level, titles, streak and the last round's reward block. **No transfers:** nothing in the server moves coins or gems from one account to another; the only wallet writes are the ledger's single-account credit and spend and the guest merge's one-way migration on account deletion, and a test asserts exactly that.
- Missions (GDD 12.5): `content/missions/v1.json` holds the daily and weekly pools (validated by `pnpm content:validate`, replaced live through `missions_set` with the server key); each player gets three dailies drawn at local midnight and five weeklies per week from a seeded shuffle, progress is counted from round events at round end (and a voice token at a private table), a progress change sends the in-app notification `missions_progress` (code 1001), `missions_claim` pays through the ledger once per period and mission, and `missions_reroll` swaps one unclaimed daily mission a day.
- The daily reward calendar (GDD 12.6): `content/daily-rewards/v1.json` is the 7-day cycle; `daily_reward_get` shows today's and the next reward, `daily_reward_claim` pays once per local day through the ledger (key `daily:YYYY-MM-DD`, so a second device is a no-op) and moves the cycle on; a missed day changes nothing. Sign-in sends the in-app notice `daily_reward_ready` (code 1002) while today is unclaimed.
- Leaderboards (GDD 12.8): two Nakama leaderboards, `baithak_weekly` (reset Monday 00:00 UTC) and `baithak_monthly` (the 1st), authoritative and incrementing, created at start-up. The round end posts each seat's positive Baithak points (R50); points from private rooms stop at 30 a day per player (`progress.privatePointsToday`), public tables are uncapped. `leaderboard_get {board, scope: global|friends, limit?, cursor?}` pages the board or lists the caller and their friends; the reset hook pays the top ten gems through the ledger (20, 10, 5 by bracket) until the cosmetic catalog exists.
- Phone sign-in (GDD 10.2, #99, OQ-041): `phone_start {phone}` sends a code through the configured provider (Twilio Verify, or the local provider on a local box whose code is the number's last six digits) within the limits per number, account, address and day; `phone_verify {phone, code}` links a new number to the caller as the custom id `ph_<sha256(pepper:number)>` or, for a number another account holds, returns a one-time `otp:` token that `authenticateCustom` trades for that account in `beforeAuthenticateCustom`; `phone_status {remove?}`. Setup: `docs/runbooks/phone-sign-in-setup.md`.
- Ranked (GDD 7.5, 12.9, R53): `content/ranked/v1.json` holds the ladder (OQ-040). Tickets with `mode: ranked` are rebuilt in the matchmaker hook with the stored rating and a band of ±150 to ±600 at four seats; parties are refused. The matched table runs mode `ranked` (standard rules, hand-taking off, 12 s, no memory assist, no watchers). At round end the engine's pairwise Elo rates every seat, an abandoner (away over 60 s and gone at the end, R46) places last and pays a penalty, and placed players post their rating to `ranked_<season>`, a per-season board with the `set` operator. The first `ranked_get` or ranked round after a season ends pays its league reward once (ledger key `ranked:<season>:reward`) and carries half the distance from 1200. `ranked_get` returns the card, `ranked_board {limit?}` the top places. Ranked tables are never created by code.
- Achievements (GDD 12.7): `content/achievements/v1.json` lists forty across play, social, skill, collection and seasonal, each with its metric and target; the server keeps lifetime counters, streaks and the same-group count per player in `achievements`, evaluates them at round end (and the friend count on `achievements_get`), pays gems once through the ledger (`achievement:id`), adds title rewards to the player's titles and sends `achievement_unlocked` (code 1003). Houdini (escape with a single card drawn from the discard) is a highlight the Thulla host derives from the private draw, the play and the escape. `achievements_set` replaces the list with the server key.
- The content pipeline (ADR-0011, GDD 18.9): every file under `content/` carries `schema`, `id` and `version` (`pnpm content:validate`), `pnpm content:manifest` writes `content/manifest.json` with each file's hash (CI fails on drift), and the server bundles the base content. `content_manifest` returns the manifest with the RSA-SHA256 signature over `signedBytes` from `HULLA_CONTENT_SIGNATURE` (made at deploy time by `pnpm content:sign`, key named by `HULLA_CONTENT_SIGNING_KEY_ID`), unsigned otherwise; the signing happens off the box because Nakama's `rsaSha256Hash` returns raw bytes that do not survive JSON. `content_get {path}` serves a listed file's exact text with its hash; the files are bundled with `?raw` imports so the text is byte for byte what the manifest hashed. Clients pin the manifest version per session, verify the signature with the public key in the binary and the hashes per file, and keep the bundled copy for offline use.
- Server analytics (GDD 23.3, ARCHITECTURE 12.4): `services/analytics.ts` emits events typed against the generated `AnalyticsEvents` map as one structured log line each (`message: "analytics"`, fields `event`, `gameId`, `tableId`, `roundId`, `seat`, `mode` and the parameters); `match/analytics.ts` maps the public game messages (round_start, move_played, thulla, pickup, hand_taken, empty_hand_draw, endgame_draw, confirmed, escape, round_end, quick_chat, emote, disconnect, reconnect) and the RPCs add table_create, friend_add, block, report, mission_complete and chat_text. A guard refuses names, chat text, hands and cards at runtime, and a test proves it; the client emits the rest behind consent.
- Observability (GDD 20.13): `src/infra/log.ts` writes every log line with fields as JSON keys and redacts names, handles, chat text, hands, cards and tokens (a test fails on a call site that tries); `src/infra/metrics.ts` keeps the `hulla_*` counters and the round duration timer next to the analytics events (exposed as `nakama_custom_hulla_*`); Nakama serves Prometheus on port 9100; `infra/observability` holds the Prometheus scrape config, the alert rules and the Grafana dashboard, with a compose file for local use (`docs/runbooks/observability.md`).
- Remote configuration (GDD 22.5, 20.15): flags and numbers per region and cohort and the minimum client version in one storage object with bundled defaults (`services/config.ts`); `config_get {clientVersion?, cohort?}` resolves them for the box's `HULLA_REGION` (open before sign-in, so the update prompt can show), `config_set` replaces the object live with the server key (a lower version is refused), `hello` names the minimum client version, and the match binding refuses a join from an older client with `auth.update_required`. Firebase Remote Config and Crashlytics are the Unity part.
- Load test (GDD 28.1, 28.5): `infra/load/tables.js` is the k6 scenario, one four-seat table per virtual user with a drop and resume; `infra/load/README.md` has the commands, the chaos recipe and the thresholds; results go to `docs/research/load-test.md`.
- The season pass (GDD 12.10): `content/seasons/<season>.json` holds the dates, the pass XP per source (rounds, daily and weekly mission claims, doubled in the final two weeks) and forty tiers with a free and a premium reward; `pass_get` shows the running season with the caller's XP, tier and claims, `pass_claim {tier, track}` pays a reached tier once through the ledger and the inventory (coins, gems, items, a title), and `pass_premium_grant {userId, plus?}` opens the premium track for every tier already passed, Premium+ skipping ten tiers, with the server key (the IAP receipt validation of #58 calls it) and an audit row. The pass never gates play.
- Push notifications (GDD 10.10, 19.3; the server side of #43 and #46): `push_register {installId, token, platform, locale?, tzOffsetMinutes?}` keeps up to five device tokens per account in `push` (under the system user, so the sweep can page them; a refreshed token replaces its install id, a token seen on another install id moves over), `push_unregister {installId}` forgets one, `push_settings_get` and `push_settings_set {types?, quietHours?, invitesFromNonFriends?}` hold the per-type switches (friend-online off by default) and the 23:00 to 08:00 local quiet hours. Delivery is FCM HTTP v1 from the runtime (`services/fcm.ts`: a service-account JWT through `nk.jwtGenerate`, the access token cached in `push_oauth`, one `nk.httpRequest` per device; iOS goes through the APNs key uploaded to Firebase), configured by `HULLA_FCM_PROJECT_ID`, `HULLA_FCM_CLIENT_EMAIL` and `HULLA_FCM_PRIVATE_KEY`; without them nothing is sent and the in-app notices still flow. A push carries no text: the data block names the `type` and the `route` (lobby, friends, home, pass) and the title and body travel as localisation keys `push.<type>.title` and `push.<type>.body` with their arguments, so the device renders them from its own string table. Dead tokens (404 UNREGISTERED) are dropped at once, tokens not refreshed for sixty days or failing ten times in a row at the sweep. Triggers: `table_invite {userIds}` invites up to ten players to the table the caller sits at (an in-app notice 1004 with the code, a push that friends get even in quiet hours; twenty an hour per sender, blocked players and those who muted invites from non-friends are named in `skipped`); the `AddFriends` after-hook and `friend_add_by_code` push a friend request that is not yet mutual; sign-in pushes "came online" to the players who pinned the account (opt-in, at most once an hour per friend, not for a sign-in within ten minutes of the last); `admin_push_sweep` (hourly from the cron sidecar) sends the daily reward once a day after 09:00 local while today is unclaimed and the season end once in the season's last 24 hours. `admin_push_test {userId, type}` sends one push regardless of settings to check a device. Setup is `docs/runbooks/push-and-purchases-setup.md`.
- In-app purchases (GDD 13.4, 20.9; ARCHITECTURE 8.10; #58): `content/products/v1.json` lists the products with the id used on both stores, the USD reference price and the grants (Remove Ads, the five gem packs, the premium pass and Premium+, the starter bundle with 200 gems, a card back and a frame). `economy_products` serves them with the caller's entitlements; `iap_verify {store, receipt}` hands Unity IAP's receipt payload (the base64 App Store receipt, or Google's `{"json":...,"signature":...}` string) to Nakama's Apple or Google validator and grants every validated purchase once, with `iap:<store>:<transactionId>` as the ledger key, so a resend, a restore or the after-hooks of Nakama's own validation endpoints never pay twice; a tampered receipt answers `economy.receipt_invalid` and leaves a warning and a metric, a box without the store credentials (`iap.apple.shared_password`, `iap.google.client_email` and `private_key` in the Nakama config) answers `economy.store_unavailable`. Entitlements (Remove Ads, frames, what was bought, a premium pass bought between seasons that `pass_get` opens when a season runs) live in `entitlements` per account and ride along in `wallet_get`; `iap_restore` re-applies every transaction Nakama holds for the account on a new device. Each grant writes an audit row and the `purchase` analytics event. Refunds are not revoked automatically (OQ-033).
- Rewarded ads (GDD 13.6, 20.9; ARCHITECTURE 8.10; the server side of #60): a reward is granted only from AppLovin MAX's server-to-server callback. The ad unit's callback URL is `https://<box>/v2/rpc/ad_reward?http_key=<key>&unwrap&user_id={USER_ID}&event_id={EVENT_ID}&token={EVENT_TOKEN}&custom={CUSTOM_DATA}`; the server checks the token (the SHA-1 of the event id and the event key the box holds in `HULLA_APPLOVIN_EVENT_KEY`), refuses a session that calls it, and answers every call with a 200 so AppLovin does not retry a refusal. The client's custom data on the ad names the placement: `double_coins:<tableId>:<roundId>` doubles the last completed round's coins (`progress.lastReward`), `reroll` earns an extra mission re-roll that `missions_reroll` spends after the free one, `theme_trial:<itemId>` starts a 24-hour trial of a table theme (`inventory.trials`; equip works until it ends). Every event id pays once (ledger key `ad:<eventId>`), each placement stops at its daily cap per local day (`ad_rewards`), and the caps (`ad_cap_double_coins` 5, `ad_cap_reroll` 2, `ad_cap_theme_trial` 1) and the interstitial rules (`interstitials`, `interstitial_from_round` 4, `interstitial_interval_seconds` 240) are remote-configuration flags. `ads_get {tzOffsetMinutes?}` tells the client today's use, the credits and the interstitial rules, off for an account that holds Remove Ads. Interstitials, consent and ATT are the client's. Setup is `docs/runbooks/push-and-purchases-setup.md`.
- Draining for deploys (GDD 20.15): `admin_drain {on, reason?}` (server key or owner, audited) makes the node refuse new tables and matchmaker tickets with `table.draining` while running tables play to their end; it reports `liveTables` so a deploy can wait for zero, and `hello` shows `draining`. The blue-green procedure is `docs/runbooks/deploy-and-rollback.md`.
- Look feedback (the theme playtest): `look_feedback {look, rating, keep, comment?, rounds?}` keeps one answer per player and look (`basant` or `pop`, the list in `services/look_feedback.ts`) in `look_feedback`, server-only, a later answer replacing the earlier one; `admin_look_feedback` (server key or owner, audited) returns per look the count, the average rating, the share that would keep it and the newest 200 comments, with no user ids. The `looks_test` flag (on by default) lets the owner turn the prompt off.
- The shop and the collection (GDD 12.11, 13.4): `content/catalog/v1.json` lists the cosmetics with category, rarity, price (coins for common and rare, gems for epic and legendary) and Addressables address; starters are owned by everyone. `economy_catalog` returns prices, ownership, what is equipped and the weekly spotlight; `economy_purchase {itemId}` pays through the ledger once per item (`purchase:item`, so a retry is a no-op); `inventory_equip {itemId, gameId?}` equips everywhere or per game and the seat's `cosmetics` in `table_state` show it at the next round; `catalog_set` reloads the catalog and `admin_grant` credits coins or gems for support, both with the server key and the grant audited.
- `src/services/account_merge.ts` and `src/rpc/account_merge.ts`: guest progress merges into a linked account. While still the guest, `account_merge_prepare` issues a one-time code (ten minutes); as the linked account, `account_merge` redeems it: stats add up, the wallet adds up (OQ-015), streaks and name changes take the larger, the linked account keeps its handle, friend code and privacy and its name unless it still wears the generated guest name; the guest's round history moves over and the guest account is deleted. Linking itself is Nakama's own link endpoints from the client. One table session per account: a second device joining a seat whose session is live is refused with `auth.device_limit`; a client that proves it held the seat with the resume token takes over.
- `src/hooks/before_channel_message.ts`: table text chat rides a Nakama room channel named after the match id (ADR-0018); before a message is delivered the hook enforces 140 characters, no links or phone numbers, one message per 2 s and ten per minute per account, with timestamps in the `chat_rate` collection. A refusal is a thrown error, which Nakama logs at error level and returns to the sender. Quick chat and emotes are match data: the core checks the phrase or emote id against the bundled packs (`content/quick-chat`, `content/emotes`), applies a 3 s cooldown per sender and broadcasts `quick_chat_sent` or `emote_sent` with the sender's seat; spectators may not send them.
- `src/hooks/matchmaker_matched.ts`: Quick Play. When Nakama's matchmaker forms a group, the hook opens a public table for exactly those players (standard preset locked, parties flagged) that deals itself once they are seated or when the join window closes with at least three (GDD 7.2, 9.5, 9.6). `config/local.yml` runs the matchmaker every 5 s and accepts the minimum of three on the fourth pass, so a search that nobody fills starts at the 20 s mark (OQ-006); the client widens its query at 10 s and 15 s.
- `src/services/account_deletion.ts` and `src/rpc/account.ts`: in-app deletion with a 14-day grace period. `account_delete` records a request in `deletion_requests`, `account_delete_cancel` withdraws it, `account_export` returns Nakama's account export (storage, wallet, friends, chat) with the profile and any pending request. `admin_purge_deleted` (server to server, http key, no user) deletes every account whose grace has passed, at most 50 per run: it tombstones the player id in its round logs (found through the per-player `round_results` objects written at round end), frees the friend code, logs the sessions out and deletes the Nakama account; `{"dryRun": true}` lists what would go. The cron sidecar (#76) calls it daily.
- `src/services/profiles.ts` and `src/rpc/profile.ts`: profiles in the `profiles` storage collection (owner-readable, server-written), bootstrapped by the after-authenticate hooks (`src/hooks/after_authenticate.ts`) with a guest name, the first presets from `content/avatars` and an 8-character friend code claimed in `friend_codes`. `profile_get` serves the owner everything, friends the card plus the friend code, strangers the card, and nothing when the profile is friends-only; `profile_update` validates names (2 to 20 code points, any script), handles (unique through the Nakama username), avatars, flag, bio and privacy, and allows one free display-name change. The stats card moves after every completed round from the game host's per-seat highlights (`GameHost.highlights`), read from the round's logged messages.
- `src/match/`: the table core, the generic match handler behind every game (ARCHITECTURE 7.2, 8.3 to 8.6). `table_core.ts` owns the lifecycle (lobby, in round, round ended, closing), the message pipeline (envelope and schema validation, seat and phase checks, idempotency by seat and clientSeq), deadlines and the auto-play policy, the message log with sequence numbers and state hashes, snapshots, redaction dispatch, the rematch loop and series state. `round.ts` seeds and deals rounds, applies moves and fires deadlines; `lobby.ts` holds seat and host rules; `log.ts` and `view.ts` build the log and the per-viewer `table_state`. `nakama_match.ts` adapts the core to Nakama's match callbacks. A game plugs in through the `GameHost` interface in `types.ts`, which wraps its engine module with wire encoding; the core knows no game.
- `src/infra/nk.ts`: the narrow interface over `nk` and the logger that services depend on; `src/__tests__/fake-nk.ts` fakes it for unit tests.
- `scripts/build.mjs`: esbuild bundles `src/main.ts` into `build/index.js`, lowered to ES2015 for goja. The bundle is git-ignored and built in CI.
- `config/local.yml`: Nakama config for local development with placeholder secrets; deployed boxes replace them.
- `compose.yml`: Postgres and Nakama for local development, with the bundle and config mounted. Deployment overlays live in `infra/compose/`.
- `Dockerfile`: Nakama plus the bundle and configs; `server-image.yml` builds it on `main`.

## Match handler notes
- Nakama freezes everything reachable from the global object after InitModule and rebuilds the match state as plain data between callbacks: validators are created per call (`createChecks()`), the state holds records and the PRNG words, never Maps or instances (ADR-0022).
- Voice is off until the box sets `LIVEKIT_URL`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` in `runtime.env`; until then `voice_token` answers `voice.unavailable`. The compose file runs a local LiveKit with matching keys.
- Nakama resolves RPC and match callbacks by their global function names, so every registered handler is a named top-level function and `registerMatch` receives identifiers, never literals.
- Only public messages advance the table sequence number; seat-only messages carry the current one and are logged against their seat, so every client sees a gap-free stream and a reconnect replays exactly what that seat may see.
- Nakama's `matchJoin` has no metadata, so `matchJoinAttempt` records an admission (seat or spectator) that `matchJoin` consumes.
- Round records (seed, players, moves, result, final state hash) go to the `round_logs` storage collection under the system user at round end and when a table closes mid-round.

## Scheduled jobs
Until the cron sidecar exists (#76), run `curl -s -X POST "http://127.0.0.1:7350/v2/rpc/admin_purge_deleted?http_key=<key>&unwrap" -d '{}'` daily (`{"dryRun": true}` previews) and `admin_push_sweep` the same way every hour. Listings from `nk.storageList` and `nk.friendsList` can return a cursor on the last page, so every paging loop in the server stops on a short page or a repeated cursor.

## Runtime constraints
No Node APIs, no timers, no async in match handlers; only `nk` performs IO; every inbound payload passes the generated check before any logic runs (ARCHITECTURE 8.1, CODING_RULES 3.5).
